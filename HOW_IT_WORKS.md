## Как работает Dependency Flow — простыми словами

Обычное обновление зависимостей выглядит deceptively просто:

```text
поменять версию → обновить lockfile → запустить тесты
```

Но для большого старого проекта этого недостаточно. Если обновить пакеты по одному или взять последние версии, почти наверняка получится несовместимая комбинация. Поэтому Dependency Flow фактически решает задачу планирования безопасной миграции.

### 1. Фиксируется исходная точка

Baseline — это фотография состояния проекта:

- какие зависимости установлены;
- насколько они отстают;
- какие проблемы и уязвимости уже существовали;
- какие проверки проходили до миграции.

Baseline можно переснимать, начиная новый цикл оценки. Он нужен, чтобы отличить новую поломку от проблемы, которая уже была в проекте.

### 2. Строится карта совместимости

Программа не просто смотрит на последние версии. Она собирает:

- доступные версии из настроенного registry;
- peer dependencies;
- ограничения React, TypeScript, ESLint, Vite и других экосистем;
- наличие реального tarball;
- исключения, заданные пользователем;
- допустимый уровень отставания.

Например, новая версия `vitest` может требовать новый `vite`, новый `vite` — другой plugin, а внутренний пакет проекта при этом разрешает только старый major. Это уже не независимые обновления, а одна связанная система ограничений.

### 3. Solver ищет совместимую комбинацию

Peer solver перебирает кандидатов и ищет назначение версий, при котором зависимости не противоречат друг другу.

Условно:

```text
vitest A требует vite >= 5
plugin-react B поддерживает vite 4–6
a shared package may constrain a bundler major
```

Solver должен либо найти общий вариант, либо доказать, что текущая цель недостижима без расширения scope.

Именно здесь появляются сообщения про тысячи candidates и лимит в 50 000 состояний. Это не 50 000 установок — это перебор возможных комбинаций версий.

### 4. Жадный алгоритм выбирает достаточный набор

После поиска совместимых версий программа определяет, сколько обновлений действительно нужно для достижения выбранного уровня — например Yellow.

Она старается:

- сначала брать наиболее полезные обновления;
- не затрагивать лишние пакеты;
- сохранить небольшой запас над границей уровня;
- не выбросить обязательную или критическую цель;
- не нарушить найденную совместимость.

То есть цель — не «обновить всё», а «получить минимальный воспроизводимый набор, который честно достигает нужного состояния».

### 5. Пакеты самостоятельно разбиваются на группы

Группы теперь не являются ручным источником истины. Алгоритм объединяет связанные пакеты в compatibility cohorts и раскладывает независимые части по небольшим веткам.

Например:

- React и его UI-библиотеки должны идти вместе;
- TypeScript ESLint parser и plugin — вместе;
- независимый CSS plugin можно обновлять отдельно.

Это позволяет запускать несколько миграций параллельно, не создавая конфликтующие изменения в одном `package.json` и lockfile.

### 6. Каждая группа работает в отдельном Git worktree

Для группы создаётся собственная рабочая директория и ветка. Агент там:

1. Проверяет точный scope.
2. Меняет manifest.
3. Перестраивает lockfile.
4. При необходимости адаптирует конфигурацию.
5. Запускает установки, lint, build и тесты.
6. Записывает evidence.
7. Коммитит только подтверждённый результат.

Главная ветка проекта при этом остаётся свободной для последовательной интеграции.

### 7. Результаты сливаются последовательно

Исполнять группы можно параллельно, но сливать их безопаснее по очереди.

После каждого merge повторяется cumulative verification. Это важно: две ветки могут проходить проверки отдельно, но конфликтовать после объединения.

Поэтому схема выглядит так:

```text
параллельное выполнение
        ↓
последовательный merge
        ↓
общая проверка проекта
        ↓
следующий merge
```

### 8. После изменений roadmap пересчитывается

Программа снова анализирует фактический `merged`:

- действительно ли достигнуты target-версии;
- сколько целей подтверждено;
- остались ли actionable dependencies;
- достигнут ли Yellow;
- не появились ли новые проблемы.

Если остался небольшой хвост, создаётся continuation-план только для него. Уже завершённая работа повторяться не должна.

### 9. Planner нужен только для неоднозначных ситуаций

Большинство известных случаев теперь обрабатывается обычным кодом:

- обновить устаревший roadmap;
- продолжить сохранённый worktree;
- временно отложить занятую ветку;
- запустить зелёные sibling-группы.

Модельный Planner вызывается, когда требуется настоящее решение:

- текущего плана недостаточно для Yellow;
- нужна дополнительная существующая dependency;
- возникла неоднозначная Git-топология;
- разные варианты исправления меняют scope;
- совместимость нельзя восстановить локально.

## Почему это долго

Основные причины:

- Для десятков зависимостей загружаются сотни и тысячи вариантов версий.
- Registry и tarball-проверки зависят от сети и registry.
- Solver исследует большое пространство совместимых комбинаций.
- `yarn install` и перестроение большого lockfile сами по себе дорогие.
- Проверки выполняются не один раз, а внутри группы и после интеграции.
- Агент сначала изучает конфигурацию проекта, потому что обновления ESLint/Vite/TypeScript часто требуют не только смены версии.
- После неудачной комбинации полезные изменения сохраняются, а residual scope пересчитывается.
- Параллельное выполнение ограничено конфликтами и последовательной интеграцией.
- Значительная часть времени — ожидание model provider, registry и package manager, поэтому низкий CPU не обязательно означает зависание.

По сути, Dependency Flow — уже не просто dashboard. Это небольшой миграционный оркестратор: он строит план, решает зависимости, управляет Git-ветками, запускает агентов, проверяет результат и умеет продолжать работу после частичных неудач. Именно безопасность и воспроизводимость делают алгоритм сложным — и одновременно позволяют не разбирать вручную десятки конфликтующих обновлений.
