# DepLoom Desktop

Основной пользовательский продукт DepLoom. Electron Control Plane запускает bundled Python core из того же release, управляет Git/worktree, agent sessions, recovery/merge/release state и показывает прогресс. На машине пользователя нужен Python 3: `python` на Windows или `python3` на Linux/macOS.

## Development

```bash
npm ci
npm run build
npm run dev
```

## Packaging

```bash
npm run package:win
npm run package:linux
npm run package:mac:x64
npm run package:mac:arm64
```

Артефакты имеют единое публичное имя DepLoom:

- Windows x64: `release/DepLoom-Setup-<version>-x64.exe` + blockmap + `latest.yml`;
- Linux x64: `release/DepLoom-<version>-x64.AppImage` + `latest-linux.yml`;
- macOS x64/arm64: `release/DepLoom-<version>-<arch>.dmg/.zip` + `latest-mac.yml`.

`prepare-tool.mjs` кладёт portable Python dependencies и Z3 wheel **для конкретной target OS/arch** в `vendor/`, после чего packager включает их в `resources/tool`. Runtime выбирает `python`/`python3` по ОС и завершает timeout/cancel целым process tree, а не только непосредственным child.

### Статус платформ

Windows x64 и Linux x64 публикуются в GitHub Releases и считаются supported. macOS x64/arm64 уже собирается и smoke-проверяется в GitHub Actions, но **не прикладывается к публичному Release**, пока не настроены Apple Developer ID signing и notarization. Это намеренная release gate: `electron-updater` на macOS требует подписанное приложение.

## Обновления

Приложение проверяет **публичный GitHub Release `AlexanderLevenskikh/deploom`** через 10 секунд после запуска и затем каждые 30 минут. `electron-builder` вшивает GitHub feed в `app-update.yml`; runtime не использует `setFeedURL`, API-ключ или приватный registry. Windows публикует `latest.yml`, Linux — `latest-linux.yml`; macOS CI проверяет `latest-mac.yml`, но публичное macOS-обновление включится только вместе с подписанным/notarized release.

## State repository

Командный workspace остаётся **team-state repository**: Desktop хранит там настройки команды, knowledge/history, flow state и воспроизводимые артефакты, а локальные runtime caches и скачанные обновления в Git не форсируются. Это состояние общее для поддерживаемых Desktop-платформ и не является вторым orchestration backend.

## GUI PATH

На Linux/macOS DepLoom не запускает пользовательские shell startup scripts, но расширяет унаследованный **GUI PATH** стандартными `/usr/local/bin`, Homebrew и пользовательскими Volta/asdf/pnpm/local bin-каталогами. Это позволяет находить `python3`, Node/package managers и agent CLI при запуске из Dock/desktop без небезопасного выполнения `.zshrc`/`.bashrc`.

## CLI boundary

Python entry points в корне репозитория остаются low-level headless tooling (baseline/roadmap/audit/validation/branch helpers). Они **не являются полным CLI-аналогом Autopilot**. Мы намеренно не дублируем Electron state machine: orchestration, agent sessions, recovery, merge/release и persistent UI state имеют одного владельца — Desktop Control Plane.

## Работа с этапами FLOW

Строка этапа в левой колонке только выбирает его: справа показываются описание, состояние Git, связанные настройки и доступные действия. Никакая команда по нажатию на строку не запускается. Запуск, повтор или продолжение всегда выполняются отдельной кнопкой внизу карточки; действия с последствиями сохраняют подтверждение.

Повторная проверка окружения из шапки не является повтором всего FLOW: она обновляет Git и версии инструментов, не удаляя уже завершённые этапы. Если команда этапа завершилась ошибкой, подтверждённые предыдущие результаты остаются на месте. Настоящий повтор baseline, миграции или другой изменяющей команды сбрасывает только зависящие от неё последующие результаты.

## Baseline constraint solver

Перед созданием Branch plan Baseline теперь выполняет `solve → verify → learn → solve`: строит общий peer/environment graph, подбирает версии, материализует exact assignment во временном локальном clone и запускает package-manager resolver. Если комбинация не устанавливается, failing components локализуются параллельным delta-debugging и сохраняются как `nogood`; solver больше не предлагает ту же комбинацию. `constraintVerification.parallelism` управляет числом параллельных probes (по умолчанию 4).

`migration.verificationCommands` также можно запускать в Baseline как раннюю диагностику. По умолчанию (`constraintVerification.projectChecks=diagnostic`) их краснота **не меняет версии**: это работа Executor по адаптации исходного кода. `strict` разрешает считать такие падения hard constraint. Ошибки окружения (`yarn ENOENT`, сеть, temp/Git) классифицируются как INFRA и никогда не обучают solver плохому constraint.

После verified Baseline Executor не выбирает другие версии. `MIGRATION_REPAIR_EXHAUSTED` означает, что код к утверждённым targets пока не доведён. Если Executor/repair доказывает, что зелень требует изменить immutable assignment, Desktop сохраняет `DEPENDENCY_COMPATIBILITY_EVIDENCE`: та же source/config-ветка воспроизводится с candidate и pre-update control, structural regression локализуется и дважды подтверждается, и только после этого session-local nogood возвращается exact Z3. Human/agent prose само по себе solver authority не получает. Ни один из этих статусов не должен молча исключать уже сделанную группу.

## Миграция агентом

Миграция ведётся оркестратором по группам: приложение само создаёт/переключает ветку каждой группы Branch plan и само выполняет merge в `mergedBranch`. Большая Git-группа дополнительно делится только на **execution batch** (по умолчанию не более 6 пакетов на вызов модели), при этом `compatibilityCohort` атомарен и никогда не режется пополам. Это не меняет Branch plan, target или Git-группировку — уменьшается только контекст агента. Для каждого batch канонический генератор заново строит точный subset prompt и оркестратор сверяет его с полным согласованным prompt: если пакет/target/shouldUpdate расходятся, запуск останавливается с `BATCH_SCOPE_DRIFT`/`GROUP_SCOPE_DRIFT`, а не принимает новое решение молча.

Промпт для группы строится в скрытом окне, загружающем уже сгенерированный `local-dependency-roadmap.html` — это статический артефакт, который переписывает только сама генерация («Верификация» / «Актуализировать все»), а не обновление desktop-приложения. Если версия desktop ушла вперёд относительно последнего построенного отчёта, старый HTML может не содержать нужную функцию; приложение обнаруживает это явно и просит перестроить отчёт, а не падает с непонятной ошибкой.

Выбор target для группы — не независимое решение по каждому пакету, а результат общей greedy-оптимизации (см. «Выбор минимально рискованного target» ниже): исключение или изменение одного пакета может изменить, какие *другие* пакеты выбраны для действия в этом же прогоне, даже без прямых изменений в них. Поэтому «Верификация», запущенная уже после того, как prompt был выгружен, может незаметно устареть — а стадия агента прямо предупреждает об этом (сравнивая время последнего построения dashboard со временем экспорта prompt) и просит выгрузить заново, вместо того чтобы ждать `GROUP_SCOPE_DRIFT` в середине запуска. Правило простое: не запускайте «Верификация» повторно после выгрузки prompt, если не собираетесь менять scope ещё раз.

«Начать заново» — отдельная кнопка с явным подтверждением: она сохраняет tracked и untracked изменения проекта в именованный safety stash `dependency-flow-before-agent-*`, переключается на исходную ветку, **удаляет локально** work-ветки и `mergedBranch` текущего Branch plan (только их — source/release и посторонние ветки не трогаются) и забывает сохранённые сессии агента для этого проекта, так что следующий запуск действительно начинается с нуля. Обычное продолжение ничего не удаляет: оркестратор перечитывает Git и начинает с фактически оставшегося scope. ID CLI-сессии сохраняется только как средство восстановления после **реального внешнего прерывания** (Stop/закрытие приложения) и вместе с fingerprint `provider + project + branch + batch scopeHash + model + версия prompt/dashboard`. Resume разрешён только при точном совпадении; legacy-сессии без fingerprint, старый baseline/target/prompt или другой batch автоматически получают свежий контекст. Если CLI сам закончил попытку, но batch ещё не готов, следующая автономная попытка также всегда свежая — состояние переносится через Git/evidence и фактическую сводку оркестратора, а не через раздувающуюся историю чата. Поле «Модель» по-прежнему передаёт ровно выбранную пользователем модель и входит в fingerprint.

Если merge группы в `mergedBranch` конфликтует в `package.json` и/или ровно в одном lockfile (`yarn.lock`/`package-lock.json`/`pnpm-lock.yaml`) — обычный, а не редкий случай: две группы Branch plan правят непересекающиеся пакеты, но правки попадают в один и тот же блок `dependencies`, из-за чего построчный merge git считает это конфликтом, хотя по сути пакеты не пересекаются — оркестратор не останавливается на ручное разрешение. `package.json` сливается по каждому пакету отдельно относительно общего предка (пакет, изменённый только одной стороной, берётся как есть; изменённый одинаково с обеих — не проблема; изменённый **по-разному** с обеих сторон — уже содержательный конфликт); поля вне `dependencies`/`devDependencies`/`peerDependencies`/`optionalDependencies` при механическом fast-path должны совпадать дословно. Дальше lockfile (если он тоже конфликтовал) перегенерируется командой пакетного менеджера (`yarn install` / `npm install --package-lock-only` / `pnpm install --lockfile-only`), и оркестратор сам завершает merge коммитом.

Если механического fast-path недостаточно — конфликтуют исходники/конфиги, обе стороны изменили один пакет по-разному, регенерация lockfile упала и т.п. — desktop теперь не отдаёт `MERGE_HEAD` человеку сразу. Он запускает до трёх ограниченных recovery-попыток агента прямо в текущем незавершённом merge. Агенту запрещено менять ветки, отменять merge, коммитить, менять согласованные package targets или обходить проверки; он должен разрешить конфликт по смыслу, при необходимости исправить вызванные обновлением ошибки сборки/typecheck/lint/test, повторить проверки и только подготовить разрешённые файлы. Оркестратор после каждой попытки сам проверяет, что HEAD остался на `mergedBranch`, `MERGE_HEAD` всё ещё принадлежит ему, unresolved-файлов нет и `git diff --cached --check` проходит, затем сам создаёт промежуточный merge-коммит с отключёнными lifecycle hooks. После рестарта приложения pending merge сопоставляется с Branch plan по точному commit из `MERGE_HEAD`, а не по позиции группы. Только если безопасное состояние не удалось подтвердить за три попытки или `MERGE_HEAD` не принадлежит ни одной согласованной ветке, FLOW останавливается с диагностикой и сохраняет Git-состояние для следующего запуска.

Прогресс групп строится по `Branch plan` из сохранённого prompt и реальным Git refs проекта. Статус ветки описывает только её собственное содержимое: «Ожидает» — ветки нет, «В работе» — часть целей ещё не достигнута, «Готова к merge» — все цели группы выполнены, но merge не сделан, «Не в merged» — ветка ушла не в ту цель, «Завершено» — влита в `mergedBranch`. Текущий checkout отмечается отдельной пометкой `HEAD` и на статус не влияет, поэтому переключение веток агентом больше не меняет картину прогресса.

Факты по пакетам читаются из `mergedBranch`, а не из рабочего дерева: пока агент стоит на групповой ветке, её checkout содержит только её собственную группу, и раньше это давало ложное «цели scope не выполнены» по уже влитым пакетам. Экран и сообщения гейта всегда указывают, из какой ветки прочитаны факты.

Счётчик токенов в панели лога показывает стоимость только последнего запуска (не всей истории окна), а подсказка при наведении включает cache-read/cache-write отдельно от input — на моделях с prompt caching они обычно и есть основной объём числа, а не признак ошибки в подсчёте.


Кнопка «Продолжить агента» передаёт ту же сводку фактического состояния, что и автоматические повторы, ещё до старта сессии: агент не тратит первый проход на выяснение того, что оркестратор уже знает из Git. Если агент закончил сессию посреди `git merge` — конфликты разрешены на диске, но commit не сделан, — сводка прямо называет это состояние (`MERGE_HEAD`) и запрещает начинать новый merge или откатывать текущий: разрешённая работа не теряется, следующая сессия просто доводит тот же merge до commit.

На этапе агента есть необязательное поле «Заметка агенту на этот запуск» — свободный текст для непредвиденных ситуаций, которые не опишешь автоматической git-сводкой (например: «vite не трогать, REFACTOR_REQUIRED подтверждён» или «дополнительно проверь сборку Storybook»). До старта сессии заметка уходит отдельной подписанной фразой и не подменяет неизменяемый Branch plan/manifest. Во время запуска для OpenCode desktop поднимает локальный `opencode serve`, запускает рабочий `opencode run` через `--attach` и после получения session id отправляет новые сообщения прямо в эту session через `prompt_async`; то есть сообщение больше не ждёт отдельного CLI-перезапуска. В представлении «Ход» реплики пользователя показываются отдельно как «Вы», рядом с ответами агента и его инструментами — Raw-лог при этом остаётся доступен для диагностики. Если OpenCode-сессия ещё не успела появиться, текст сохраняется до ближайшей попытки. Codex и Claude пока остаются на одноразовом CLI-транспорте, поэтому для них сообщение во время работы по-прежнему попадёт в начало следующей автономной попытки.

### Verification и автоматический migration repair

После каждого execution batch агент обязан сохранять structured baseline/post evidence и `migrationOutcome=ready|repair-required|replan-required`. Даже `ready-to-commit` не является разрешением на merge: после всей группы Desktop самостоятельно запускает `migration.verificationCommands` (fallback на release gates / существующие package scripts). Новое падение возвращается агенту сразу в свежую repair-сессию. После каждого merge те же integration checks выполняются на накопительном `mergedBranch`; если красно только сочетание групп, агент получает отдельный merged-repair с неизменяемыми direct targets. Если для зелени надо поменять target или включить excluded/deferred direct dependency, это `MIGRATION_REPLAN_REQUIRED`, а не скрытый обход плана. Для группового `replan-required` Desktop записывает structured compatibility evidence и запускает deterministic `reproduce → localize → learn → Z3 re-solve`; LLM Planner не выбирает replacement version.

Planner также проверяет явные npm `peerDependencies` target-пакета против других прямых зависимостей проекта: заведомо несовместимый peer, который не обновляется в той же группе/cohort, получает `PEER_SCOPE_BLOCKED` ещё до prompt.

Release recovery использует machine JSON вместо разбора человеческого Markdown. Если hook доказывает дефект в `merged`, а prepared release состоит только из воспроизводимого staged дерева без пользовательских unstaged/untracked файлов, FLOW безопасно сбрасывает именно этот prepared release, возвращается в merged integration repair и после зелёных проверок создаёт release заново.

Успешный exit code агента не завершает шаг сам по себе: batch считается готовым только когда его package targets реально достигнуты, HEAD остаётся на согласованной ветке и рабочее дерево чистое; вся группа затем проходит прежний gate перед merge. Если агент ответил раньше, desktop до шести раз повторяет попытку, но **не resume'ит завершившийся разговор**: каждый retry получает свежую сессию, тот же неизменяемый batch prompt, короткую фактическую сводку Git с оставшимися целями и, если предыдущая попытка успела его записать, самый свежий branch state/checkpoint, созданный уже после старта текущего batch. Это убирает повторную оплату tool/chat history без уменьшения release intelligence или числа проверок. Для batch дополнительно материализуется маленький roadmap JSON с полными, неусечёнными строками только его пакетов; если такую оптимизированную копию создать нельзя, агент безопасно получает исходный полный roadmap. OpenCode/model/compaction-настройки Desktop не переписывает вообще: экономия достигается только организацией контекста и не меняет поведение модели.

Перед созданием release-ветки незакоммиченные tracked и untracked изменения аналогично сохраняются в `dependency-flow-before-release-*`; лог показывает точный commit stash и безопасную команду `git stash apply <commit>`. Автоматически накладывать stash поверх release-ветки приложение не будет.

Кнопка «Актуализировать все» запускает generator без `--only-project` и пересобирает общий HTML/JSON по всем настроенным проектам. Последние уровни проектов также восстанавливаются из append-only snapshot history, поэтому точечный запуск другого проекта не делает прежние результаты серыми.

## Независимый аудит

Для npm используется родной `npm audit`. Для Yarn Classic основной практический путь создаёт из `yarn.lock` изолированный `package-lock.json`, запускает обычный `npm audit` через эффективный npm/registry registry и сохраняет `reproduce-npm-audit.cmd`. Исходный проект не получает `package-lock.json`. Код `1` от npm означает найденные уязвимости и считается полученным результатом, если JSON разобран; код `2` остаётся признаком неполной проверки. Неизвестная дата публикации отдельного внутреннего пакета показывается как предупреждение, а не обнуляет успешно полученный аудит уязвимостей.

## Release и сохранение state

Перед release незакоммиченные tracked и untracked файлы проекта сохраняются в `dependency-flow-before-release-*`. Журнал печатает неизменяемый commit stash и команду `git stash apply <commit>`; приложение не накладывает пользовательские изменения поверх squash автоматически. Повтор после провала final gate или hook использует подготовленный staged squash, а отсутствие старой audit-папки считается нормальным.

Desktop автоматически передаёт в release все `release.finalGateCommands` из настроек проекта/команды; поле «Дополнительный final gate» в интерфейсе только добавляет разовую команду и не заменяет настроенный список. Финальный release-коммит выполняется без `--no-verify`, поэтому repository hooks действительно запускаются. Промежуточные group/merge-коммиты по-прежнему используют локальный пустой `core.hooksPath`, но это больше не означает «без проверок»: migration verification запускается самим оркестратором до merge и на накопительном merged. Repository hooks остаются сосредоточены на единственном итоговом release-коммите.

Если final gate, squash или pre-commit hook оставил подготовленную release-ветку незавершённой, это больше не откатывает уже подтверждённую «Миграцию агентом». FLOW сохраняет recovery-код и показывает отдельное поле «Recovery»: пользователь может написать агенту, что проверить, даже если исходный job уже завершился. Агент работает в сохранённом Git-состоянии без commit/push/reset/stash, после чего оркестратор повторяет тот же release с pinned source commit, настроенными `release.finalGateCommands` и сохранённой разовой gate-командой. Scope/target drift, неизвестный merge, несовпадение staged release с `merged` и другие safety-инварианты prompt не обходит. Если hook показывает, что нужен новый source/config fix в `merged`, recovery использует machine-result и при безопасно воспроизводимом prepared release автоматически возвращает FLOW в merged integration repair; release-only исправление по-прежнему запрещено. Если staged/unstaged состояние неоднозначно, автоматический handoff блокируется без destructive cleanup.

«Сохранить state» добавляет только командные настройки, history, dashboard state, `flow-state.json` и knowledge. Локальные загрузки обновлений, кеши и игнорируемые отчёты не форсируются в Git. Если новых изменений нет, этап завершается успешно без пустого коммита. Сообщения Git о будущей замене CRLF на LF информационные и сами по себе не означают ошибку.

После агента приложение проверяет не только merge всех веток Branch plan, но и фактическое достижение каждой package target из Exact compact scope manifest через канонический `validate_dependency_update.py`. Валидатор получает содержимое `mergedBranch` через временный detached worktree, поэтому проверка не зависит от того, какую ветку агент оставил в checkout, и не трогает его рабочее дерево. Невыполненные версии возвращаются агенту при автопродолжении и остаются видны в счётчике. После свежего пересчёта audit, release, state и публикация доступны только при достижении выбранного уровня без оставшихся closure-действий.

Последний этап «Опубликовать» использует сохранённое имя release-ветки, отправляет её в проекте, коммитит финальное состояние FLOW и затем отправляет командный workspace. Этап получает успешный статус только после обеих отправок.

## Security

Renderer работает с `nodeIntegration: false`, `contextIsolation: true` и sandboxed CommonJS preload. Команды запускаются без shell. Доступ к dashboard ограничен выбранным workspace через custom protocol. Git push, baseline и release остаются явными действиями пользователя.
