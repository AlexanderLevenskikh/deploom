# Продолжение миграции после обновления DepLoom

SourceSnapshot и доказательства верификации привязаны к коду инструмента. После
обновления открывать старое доказательство как новое нельзя. Обычный opener
по-прежнему отклоняет несовпадение сборки.

При материализации следующего кандидата или аудите сохранённого checkpoint
координатор использует отдельный переход:

1. Проверяет поддерживаемые schema/policy, сохранённый ключ, Git layout и все
   байты старого снимка. Manifest пересчитывается с исходной identity производителя.
2. Создаёт новую sealed копию тех же исходников с identity текущего инструмента.
3. Выполняет выбранные команды и точную проверку assignment текущим verifier.
   Зафиксированное сравнение исходных сбоев тестов сохраняется; новая исходная
   линия сбоев не создаётся.
4. Только при подтверждённом успехе атомарно публикует отдельную запись в
   `checkpoint-build-upgrades/`. Старый checkpoint, accepted delta и история
   не переписываются; переход не считается принятым обновлением пакетов.
5. Возобновляет обычную материализацию и последующую проверку кандидата.

Запись повторно используется только для совпадающих исходников, кода verifier,
assignment, команд, validation profile и resolver context. Последний включает
фактические версии Node/package manager, конфигурацию пользователя и окружение.
Оба снимка заново проверяются на целостность при повторном использовании.

RED, UNKNOWN, ошибка окружения и повреждение снимка не создают подтверждение
и не становятся ограничением совместимости пакетов. Прежний результат остаётся
сохранён. При повторе копия под той же identity переиспользуется, чтобы не
создавать новый многогигабайтный snapshot на каждую неудачную проверку.

Тесты: `python -m unittest discover -s tests/regression -p test_checkpoint_build_upgrade.py -v`.
Физические сценарии используют настоящий npm resolver и Node-команды: успешную
проверку сохранённого проекта и RED. Они не требуют доступа к пользовательскому
проекту или платному агенту.
