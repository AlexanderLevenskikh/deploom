## C1 — P1: уязвимость OSV без severity может пройти Fast и Yellow closure

**Воспроизведение production-функциями:** OSV entry `{ "id": "OSV-UNRATED" }` без `database_specific.severity` и CVSS получает `severity_rank=0`, затем `vuln_summary` выдаёт `U:1`. Для активного пакета с текущей `1.0.0`, lag target `1.0.0`, evidence выбранной `2.0.0 = U:1`, политики `maxKnownCritical=0`, `maxKnownHigh=0`, `minLagOkPct=80`:

- `_candidate_satisfies_fast_policy(..., candidate_targets={'a':'2.0.0'})` возвращает **True**. То же при текущей версии `U:1` без обновления.
- `compute_project_health` сообщает `unknown=1`, но `security_unknown=0` и статус `yellow`.
- `desktop/electron/target-closure.ts` берёт `security_unknown` с приоритетом над `unknown`. На таком численно полном health и пустом плане `targetClosureFromRoadmap(..., 'yellow')` возвращает **`reached=true`**, несмотря на `unknown=1`. Проверено вызовом собранного `dist-electron/target-closure.js`.

Причина: `_severity_at_candidate_version` парсит только C/H/M/L; `U` не проверяется. `_row_security_known` считает строку `U:1` оценённой, а `security_unknown` подсчитывает только полностью неоценённые OSV-строки. Это не регрессия B1: проверка точной версии теперь есть, но её результат неправильно интерпретируется. Зеленый CI не покрывает `U:1` на выбранной версии и в closure.

**Задание агенту:**

1. Ввести единое определение достаточности security evidence для текущей и выбранной версии: `U>0` означает обнаруженную уязвимость с неизвестной серьёзностью и не может подтверждать достижение policy. Не подменять её C/H/M/L=0. Сохранить явное отсутствие evidence (`None`/`unknown`) и доказанный ноль (`0`) разными состояниями.
2. В Fast-гейте блокировать завершение по policy, если хотя бы один активный пакет на **точно выбранной версии** имеет `U>0` или не имеет достоверных данных. Сохранить B1 (проверка всех пакетов), N2 (нет evidence ≠ safe), N3 (разрешённый остаток H проходит) и действующие лимиты C/H/M/L.
3. Согласовать health, Draft-отчёт и closure: проект с `U>0` не должен иметь `security_unknown=0` в том смысле, который closure трактует как полное покрытие. Выбрать понятное представление «уязвимость без severity» отдельно от «OSV недоступен»; не задвоить `unknown` при обновлении счётчиков. Yellow/Green closure должны оставаться `reached=false`, пока такая неопределённость не устранена; пользователю нужна явная причина.
4. Добавить failing-first тесты на реальный `vuln_summary([{'id':'OSV-UNRATED'}]) == 'U:1'`: текущая версия U:1 и кандидат 0→U:1 блокируют Fast; mixed `H:1,U:1` также блокирует; кандидаты с evidence `0` и допустимым H продолжают проходить. Проверить путь health→roadmap→`targetClosureFromRoadmap` с пустым планом: `unknown>0` не может дать Yellow `reached=true`, даже если остальные показатели соблюдены. Отдельно сохранить семантику обычного отсутствия OSV evidence.
5. Повторить профильный Python/Node регресс, Desktop build/lint, затем — если доступна интерактивная сессия — реальный Electron restart → job. В отчёте разделить проверенный browser harness и физический Electron-прогон.

Критерий закрытия: для всех активных пакетов с `U:1` на фактически выбранной версии Fast не объявляет `VERIFIED_POLICY_SATISFIED_FAST`; цель не закрывается по Yellow/Green, а отчёт показывает причину. Для `0` и разрешённого остатка известных severity поведение остаётся прежним.
