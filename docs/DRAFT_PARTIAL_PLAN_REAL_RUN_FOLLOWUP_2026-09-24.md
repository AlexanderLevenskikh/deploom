# Draft: опубликованы «нет данных» после успешной обработки части пакетов

Дата: 2026-09-24. Текущий код: v0.2.128. Приоритет: P1 для полезности Draft. Этот документ намеренно не содержит имени частного проекта, URL реестра и идентификатора реального запуска.

## Диагноз, подтверждённый реальным запуском

На проекте с 77 прямыми зависимостями Draft запущен без явного дедлайна. Новый механизм C2 выставил `deadlineSeconds=130.5` (`15 + 1.5 × 77`), то есть исправление 15-секундного лимита уже присутствовало в установленной версии. Журнал показывает 11 полностью обработанных пакетов: для них получены registry metadata (`registry metadata ready`), прошёл запрос OSV и выведено `done`. Некоторые крупные пакеты заняли 14.3, 20.9, 30.8 и 35.5 секунды. На 12-м пакете общий дедлайн истёк во время `network-read` с остатком менее секунды на публикацию. Манифест: `DRAFT_PARTIAL`, `elapsedMs≈129511`, причина `Draft deadline (130.5s) exceeded at network-read; metadata may be incomplete.`

При этом опубликованный `plan.json` сообщает `metadataKnown=0/76`, `securityKnown=0/76`, `unknown-security=77`, `proposed=0`. Даже первые 11 пакетов, успешно обработанные в журнале, имеют `status=unknown-metadata`, `latest=registry unavailable`. Одно исключение из scope объясняет разницу 76 в health и 77 в общем счётчике Draft. Эти данные доказывают, что формулировка «registry unavailable» для всех пакетов неверна: реестр отвечал, но результаты не дошли до публикации.

**Точная причина потери данных:** `_draft_local_inventory_rows` создаёт 77 строк до сети. `analyze_project` строит обогащённые `rows` в локальном списке и возвращает их только после обработки всего проекта. `main` присваивает `rows_by_project[project.name] = enriched` только после полного возврата `analyze_project`. При `DraftBudgetExceeded` внутри 12-го пакета функция не возвращает список; `_publish_draft_and_exit` получает прежний необогащённый inventory и ложно маркирует все строки как недоступность реестра. Доказано и кодом репозитория, и теми же строками в установленном tool script. Exit code 0 преднамерен для `DRAFT_PARTIAL`, поэтому обычной failure-диагностики нет.

**Почему дедлайн C2 не спас:** реальные времена отдельных пакетов не соответствуют заложенным `1.5s/package`. Draft выполняет сетевой анализ последовательно: `_prefetch_registry_metadata` отключён при наличии дедлайна. Уже первые 11 пакетов израсходовали почти весь бюджет. Вдобавок `_deadline_bounded_read` читает registry JSON по одному байту (`iter_content(chunk_size=1)`); локальная проба дала около 0.46 секунды CPU на 1 MiB даже без сети. Это измеренный вклад в стоимость чтения, но не доказательство, что он единолично объясняет все 20–35 секунд на крупном пакете. Draft также проверяет tarball и его содержимое при выборе кандидата, хотя задача режима — быстрый теоретический план. Простое увеличение общего лимита или его снятие не устраняет потерю уже собранных данных и не гарантирует разумную скорость.

## Задание агенту

1. Сделать публикацию **покомпонентной и атомарной**: после полного обогащения очередного пакета безопасно сохранять его `DependencyRow` в Draft-снимок проекта. При дедлайне или ошибке на следующем пакете публиковать завершённые строки вместе с inventory для остальных. Не публиковать наполовину изменённую строку и не разрешать запоздалому network worker менять уже опубликованный снимок. Сохранить устойчивую привязку к package/kind и порядок пакетов.
2. Развести причины отсутствия данных: `not attempted before deadline`, `registry request failed/HTTP`, `OSV unavailable`, `unrated vulnerability`. Не использовать `registry unavailable` для строки, к которой запрос ещё не дошёл. В итоговом prompt и UI показывать `обработано X/77`, `metadataKnown X/76`, число ожидающих и конкретную причину частичности. Исключённые пакеты показывать отдельно от активного scope.
3. Ускорить именно Draft: сначала собрать **теоретические цели** из registry metadata для всех доступных пакетов, затем обогащать OSV и дополнительные доказательства. Не блокировать появление Draft-плана на полной проверке tarball/type/runtime и физической совместимости; явно помечать такие цели `PLANNING_ONLY` и требовать их проверки агентом позже. Сохранить запрет на foreign-registry target и честное поведение при недоступном OSV. Ограничить число одновременных запросов; результат каждой завершённой задачи коммитить из основного потока.
4. Сохранить ограниченные per-request/per-package таймауты и мягкий бюджет всего запуска; не превращать сбой одного медленного пакета в «нет данных» для остальных. Оптимизировать чтение многомегабайтного JSON без байтового цикла, но **сохранить абсолютную отсечку** для медленно капающего body/header и тесты T4. Если общий бюджет истёк, завершить с полезным `DRAFT_PARTIAL`, а не с пустым prompt. Разрешить пользователю увеличить бюджет, когда он хочет полный охват, но не делать это единственным исправлением.
5. Добавить failing-first интеграционный тест: локальный mock registry с несколькими быстрыми и одним зависающим/очень медленным пакетом, дедлайн во время последнего чтения. До фикса — `metadataKnown=0` несмотря на успешные предыдущие пакеты; после — `metadataKnown` равно числу завершённых пакетов, в `plan.json` и prompt есть их теоретические targets, медленный и ещё не начатые пакеты имеют разные причины неизвестности. Проверить, что late worker не меняет артефакты. Отдельно проверить крупный ответ registry и body/header trickle, чтобы оптимизация не сломала deadline safety.
6. Не считать зелёными только 3-пакетные тесты C2 с маленьким mock-packument: они проверяют scale и доступный реестр, но не сохранение прогресса большого проекта. Приёмка должна включать новый запуск на реальном 77-пакетном проекте в установленной сборке с обезличенным отчётом: `metadataKnown>0`, `unknown-security<77` при успешных OSV-ответах, `proposed>0` если среди обработанных есть обновляемые пакеты; данные уже завершённых пакетов сохраняются при любом дедлайне. Для полного `DRAFT_READY` — все доступные метаданные обработаны. Нельзя заявлять полную проверку без такого запуска.

Не маскировать результат статусом READY при незавершённом scope. Текущий честный `DRAFT_PARTIAL` допустим, но он должен содержать всё уже доказанно собранное и не утверждать, что доступный реестр недоступен.
