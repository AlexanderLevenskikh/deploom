**2. Почему Draft медленный и почему появляется ошибка**

Флаг `--draft-baseline` действительно обходит `resolve_peer_compatibility_with_verification`, публикацию ProofEnvelope и baseline snapshot. Сам по себе Draft не запускает обычный physical verification pipeline. Это работающая часть реализации, которую надо сохранить.

Однако `source_baseline_mode = capture_baseline or draft_baseline` включает общий preflight. Если sourceCheckoutGuard включён в настройках, вызывается ensure_source_checkout с получением исходной ветки. Lockfile проходит общий ensure_lockfile_consistency; отсутствующий/несогласованный lockfile способен остановить теоретическое планирование. Явная конфигурация lockfile update также требует отдельного запрета для Draft.

Дальше выполняются analyze_project, registry metadata и OSV для кандидатов, проверка доступности пакетов, часть проверок tarball/type declarations, точное peer-планирование yellow/green/default, финальная peer-валидация. Число кандидатов по умолчанию не ограничено (`maxCandidates=0`); HTTP timeout по умолчанию 30 секунд на запрос, registry metadata имеет retries. Prefetch уже распараллелен — проблема не сводится к отсутствию параллельности. LiveDataClient начинает с пустых внутренних cache; offline-first контракт для Draft отсутствует. Release intelligence включён по умолчанию, выполняется до записи результата и не имеет отдельного короткого Draft-бюджета.

Ошибка FINAL_BASELINE_COMPATIBILITY_INVALID применяется и к Draft. Для Verified такой отказ может быть корректным; для теоретического результата следует сохранить обнаруженные конфликты и UNKNOWN, а не терять весь план.

Функция `buildPromptFromCurrentView` внутри генерируемого HTML умеет добавить заголовок DRAFT BASELINE / PLANNING ONLY (`dependency_live_roadmap_generator.py:19388`). Наличие функции экспорта в HTML не означает, что prompt-файл автоматически создан. В текущем завершении Draft такого вызова/сохранения нет. IPC preview читает `details.projectPromptPath`, то есть уже зарегистрированный отдельный файл (`main.ts:6079–6100`). Поэтому наблюдаемое сообщение полностью объясняется кодом даже при успешной генерации отчётов.

Дополнительные проблемы watcher: он создаётся после `await onRun`, при этом useDependencyFlow.runAction ловит ошибку запуска без повторного throw (`useDependencyFlow.ts:454–479`). Диалог может закрыться и поставить watcher даже при неуспешном старте. Проект проверяется по имени, workspace/run identity отсутствует. Путь preview определяется текущим выбором проекта, а не конкретным запуском.

**3. Задание агенту: обязательный результат**

Сначала обеспечить гарантированную выдачу полезного Draft, затем ограниченный быстрый режим, после этого глубокий режим и полную приёмку по выбранной политике. Не ограничиваться заменой текста/спиннера. Не включать install/build/audit внутрь Draft ради получения «проверенного» статуса. Не ослаблять защиту verified proof, границы Git/worktree и release gates.

В каждый принятый запуск добавить устойчивые `runId`, `workspaceId`, `projectId`, `mode`, snapshot настроек и `policyHash`. Результат хранить отдельно от процесса. Предлагаемые терминальные состояния: DRAFT_READY, DRAFT_PARTIAL, VERIFIED_READY, VERIFIED_PARTIAL, BUDGET_EXHAUSTED, CANCELLED, FAILED. Для VERIFIED_PARTIAL обязательно хранить точный проверенный scope и список непройденных/непроверенных gates; не подразумевать успешность полного проекта.

Успешный exit процесса без валидного result manifest не считать пользовательским успехом. Ответ о завершении должен содержать resultId/artifactId, статус, полноту данных и summary; UI читает результат конкретного запуска. Получение результата должно работать после повторного открытия приложения, перехода между вкладками/проектами и пропущенного IPC-события. Избавиться от mtime/size/seenRunning как механизма определения результата.

«Всегда выдаёт результат» означает: для читаемого package.json план или частичный план с ограничениями; для некорректного ввода/недоступного диска — конкретная диагностическая ошибка. Не обещать успешный план при невозможности прочитать проект. Недоступная сеть не должна уничтожать уже собранный Draft.

**4. Контракт трёх режимов**

| Режим | Что делает | Что получает пользователь | Условие остановки |
| --- | --- | --- | --- |
| Draft | Читает локальные manifest/lockfile, применяет scope/policy, использует cache и ограниченное обогащение metadata, строит один выбранный вариант | Теоретический план, готовый промпт, известные риски, список неизвестного, NOT_VERIFIED | Первый полезный план или короткий deadline; offline — частичный результат |
| Быстрый | Получает Draft, проверяет ограниченное число кандидатов, выбранный package-manager и согласованные checks | Проверенный результат при успехе либо Draft/частичный результат с точной причиной | Первый подходящий проверенный результат, отмена или общий бюджет |
| Глубокий | Улучшает сохранённый лучший результат, пробует дополнительные наборы и локализует конфликты | Лучший доказанный результат плюс объяснение недостигнутых критериев | Выбранная цель достигнута, дальнейших улучшений нет, отмена или общий бюджет |

Сделать `mode` продуктовым выбором, независимым от «автономно / подтверждать существенные действия». Legacy executionMode/searchMode оставить внутри адаптера, задокументировать преобразование и миграцию настроек. Учитывать, что сейчас Desktop явно передаёт maxExpensiveAttempts из бюджета и тем самым заменяет стандартный FAST limit=2 из Python.

Для Draft не выполнять git fetch/switch, изменение lockfile, установку пакетов, lifecycle scripts, project checks, обязательные release notes и обязательную загрузку tarball. Проверки доступности/совместимости можно отложить и явно отметить. Metadata cache привязать к registry, настройкам доступа и свежести; не сохранять/показывать credentials. Не придумывать версии при отсутствии metadata: сохранить current/requested и инструкцию агенту уточнить target.

Не решать все yellow/green/default синхронно ради одного выбранного результата. Опциональное обогащение должно обновлять Draft после первой публикации и не отнимать уже выданный результат.

Предлагаемые приёмочные ориентиры, которые нужно измерить, а не объявить выполненными: первый статус ≤1 секунды; локальный черновой результат ≤2 секунд на tiny fixtures; готовый Draft на тёплом cache ≤5 секунд; cold/offline deadline по умолчанию 15 секунд с переходом в DRAFT_PARTIAL. Для fast предложить бюджет 2–5 минут, число дорогих попыток 1–2; для deep — 15–30 минут с настройкой. Долгая физическая проверка не обязана уложиться: на deadline вернуть честный достигнутый статус и причину. Замерять end-to-end от нажатия до доступного артефакта.

Единый monotonic deadline создавать при принятии запуска. Передавать remaining budget в HTTP, solver, copy/install/check subprocess и worker; учитывать retries и подготовку. Не обнулять бюджет при переходе между вариантами/проектными компонентами. Явное «Продолжить» может дать новый транш. Сохранять лучший результат до остановки; непроверенный кандидат не может заменить verified incumbent.

Draft хранить в отдельном пространстве артефактов, например `artifacts/runs/<runId>/draft/`. Не менять latestVerifiedRoadmap/latestVerifiedPrompt/proven-dependency-state/checkpoint предыдущего verified-run. Добавить отдельный latestDraftResult. Для путей использовать collision-safe identity: текущая нормализация project.name в stem способна склеивать разные имена; имена только для отображения.

**5. Готовый промпт как обязательный артефакт Draft**

Публиковать атомарно `result.json`, `plan.json`, `prompt.md` и краткий summary; при сбое записи не объявлять READY. Manifest включает run/project/workspace identity, mode, inputHash, policyHash, generatedAt, полноту metadata, пути/хеши артефактов и причину частичности.

Формирование промпта вынести из зависимости от видимого Dashboard/DOM в доступный генератору или Electron сервис. Не использовать verified Branch plan parser как обязательное условие для planning-only prompt. Prompt должен включать цель и критерии, исходные зависимости, конкретные известные targets, запреты/keep-current, конфликты/unknown и необходимые проверки у агента. Явно указать NOT_VERIFIED / PLANNING_ONLY; подготовленный draft не является допуском Executor к verified FLOW.

Показать результат прямо после завершения: «Черновой план готов: предложено N обновлений; для M пакетов нужно уточнение». Кнопки: «Скопировать промпт», «Сохранить», «Открыть план», «Проверить в быстром режиме». Нулевой список обновлений — полноценный результат с объяснением. Ошибка сети: «Данные получены для 18 из 24 пакетов. Черновик сохранён, 6 пакетов требуют уточнения», с повтором обогащения. Ошибка файла: точный путь и причина, кнопка диагностики; не общий alert про ненайденный artifact.

**6. Понятный прогресс без панели приборов**

В основной карточке оставить режим, текущую операцию, счётчик, прошедшее время и состояние результата. Под раскрываемым «Ход работы» показать человеческую ленту этапов. Сырые stdout/stderr — на дополнительном уровне диагностики.

Draft: чтение проекта → сбор версий → построение предложений → сохранение плана и промпта. Fast/deep добавляют создание изолированной среды → разрешение/установка → конкретные checks → сохранение результата → при необходимости следующая попытка. В ленте показывать пакет/команду, начало, длительность, завершение, retry и его причину. Серверный heartbeat каждые 1–2 секунды даже при молчащем subprocess; `lastHeartbeatAt` отделить от `lastMeaningfulProgressAt`.

Единое событие процесса: runId, sequence, mode, phase, status, messageCode/args, completedUnits, totalUnits, unit, startedAt, elapsedMs, lastHeartbeatAt, budgetRemainingMs, attempt, bestResultId, optional errorCode. Сохранять события и последний snapshot; фильтровать по workspace/project/run, игнорировать поздние события завершённого run. Не строить пользовательский статус только парсингом произвольного stdout.

Проценты разделить: готовность конечного этапа (18/24 = 75%), расход бюджета и достигнутая актуальность (например 82%). Для неизвестного объёма поискового пространства не рисовать точный процент общего завершения. Допустима явно помеченная оценка; не использовать расход бюджета как процент готовности. 100% Draft означает, что артефакты доступны, а не что проект проверен или цель достигнута. Каждая попытка deep имеет собственный прогресс без сброса «выполнено» всего запуска.

Показать «Получаем версии uuid: попытка 2/2; прошло 8 секунд», а не вечный спиннер. При длительном отсутствии содержательного прогресса — объяснение ожидания и доступная отмена. Отмена сохраняет уже опубликованный Draft/verified incumbent, не помечает его новым доказанным успехом.

**7. Настройки перед стартом и единые критерии**

Главный экран запуска: три карточки режимов; затем «Какой результат нужен?» — Жёлтый / Зелёный / Свои критерии. Настройки цели доступны до первого запуска. Далее один блок «Подробнее»: область зависимостей, персональные исключения/обоснования, бюджет и автоматизация. Технический алгоритм не должен быть обязательным знанием пользователя.

Предлагаемый текст настроек:

- «Не менее [80]% зависимостей должны отставать от последнего стабильного релиза не более чем на [12 месяцев]».
- «Critical: 0», «High: не более [1] пакета».
- Для зелёного: «Актуальность 100%, Critical 0, High 0; Moderate и Low — заданные малые пределы».
- «Показывать частичный результат, если цель пока недостижима» — да; он не обозначается как достижение цели.

Зафиксировать смысл «без лага»: текущая реализация lag — разница дат релиза относительно последнего релиза пакета (`min_by_lag`, строка 3262), а не возраст версии относительно сегодня. По умолчанию допускает 12 месяцев; поддерживает 3/6/9/12 (`normalized_lag_months`, строка 3839). Требование «нет лага» может означать 100% в этом окне либо буквально latest stable. Предложить два явно подписанных варианта: «В пределах допустимого отставания» и «Последние стабильные версии». Не называть 12 месяцев буквальным нулевым отставанием.

В качестве стартовых пресетов: Yellow — ≥80% в окне 12 месяцев, C=0, H≤1; Green — 100%, C=H=0, M+L≤2. Число 2 — предлагаемая конкретизация слова «единичные», не установленное требование пользователя; сделать редактируемым и показать при старте. Для буквального «без лага» Green предложить latest-stable. При изменении пресета сохранять все пороги, а не сбрасывать скрыто.

Единый versioned policy должен включать freshness mode/window/minPercent, vulnerability limits, область подсчёта, исключения и критерии полноты. Передавать его UI → Electron → Python planner → prompt → audit/closure/release; сохранять snapshot/hash в результате. Пороги применяются к фактическому независимому аудиту и отдельно к прогнозу. «Прогноз цели достигнут» у Draft не означает «цель достигнута».

Устранить магические 80%, 85% planning reserve и M+L≤20 в местах расчёта Python и HTML. Planning reserve можно сохранить как явно описанную внутреннюю надбавку, ограниченную 100%, производную от пользовательского порога. Изменение цели должно менять выбор targets и условие завершения, а не только подпись карточки. Обновить старые тесты, которые запрещают freshness/target: они фиксируют отвергнутые пользователем требования.

Отдельно показывать: проверен ли проект; выполнена ли security policy; выполнена ли freshness policy. Полное принятие — их согласованная комбинация для выбранного verified режима. Допущения fast показывать явно; пропущенные обязательные checks не считать пройденными. Best-effort/частичный результат доступен для просмотра и дальнейшей работы, но не получает цвет/текст «цель достигнута».

Не менять знаменатель метрики через keep-current/deferred. Это ограничения на изменения, а не автоматические исключения из здоровья. Явное исключение из scope требует отдельного действия и причины; рядом показывать охват проекта. Unknown metadata не считать свежестью и не удалять молча из знаменателя. Сейчас unknown исключаются из total известных lag-target, и удалённые зависимости могут добавляться как removed_closed; определить и закрепить выбранную математическую модель. Процент считать с точным ceil: для 6 пакетов при 80% нужно 5, не 4. Показать числитель/знаменатель.

Уязвимости сейчас считаются неодинаково: acceptance использует количества уязвимых имён пакетов, старый health суммирует counts строк. Выбрать и подписать единицу; предложено — число уникальных уязвимых пакетов по максимальной severity. Отдельно отображать advisory count при необходимости. Полный граф security включает транзитивные зависимости; keep-current не освобождает их от аудита. UNKNOWN severity и неполный audit не равны отсутствию уязвимостей.

**8. Примеры для ручной проверки**

В репозитории есть `examples/synthetic_projects/README.md` и `materialize.py`. Шаблоны содержат package.template.json; скрипт превращает их в самостоятельные Git-репозитории и создаёт lockfile через npm install --package-lock-only --ignore-scripts --no-audit --no-fund.

Команда из корня DepLoom в PowerShell, с новым каталогом на каждый запуск:

```powershell
$fixtureOutput = Join-Path $env:TEMP ('deploom-synthetic-' + [guid]::NewGuid().ToString('N'))
python .\examples\synthetic_projects\materialize.py --out $fixtureOutput
```

Затем добавить созданный репозиторий в Desktop. Нужны npm/Node, Python, Git и доступ к registry для создания lockfile. Команда здесь приведена для пользователя; во время аудита генератор fixtures не запускался. Выбирать каждый раз новую папку: текущий materialize.py удаляет уже существующую папку одноимённого примера.

Порядок: tiny-basic (один uuid); tiny-types-stub (uuid и старый @types/uuid); tiny-vite-vitest (Vite/Vitest compatibility); nested-single-package (выбирать корень Git, package.json находится в frontend).

Это реальные package-manager примеры, но у всех четырёх manifest нет scripts: они не доказывают полный build/test/migration/release процесс. `examples/synthetic_baseline_scenarios.py` проверяет модель в памяти и также не заменяет интеграционный прогон. Для полного FLOW агент должен добавить небольшой проект с настоящими build/typecheck/test и управляемой breaking-change миграцией; release/push проверять на отдельном локальном bare remote/одноразовом окружении.

Сделать materialize.py безопасным по умолчанию: при существующем target отказ, отдельный явный overwrite только после проверки границ каталога. Для воспроизводимых тестов использовать фиксированные metadata/advisories/clock и lockfiles; внешние live registry проверки держать отдельным smoke, иначе ожидаемые цвета и время дрейфуют.

Draft-тест должен запрещать вызовы physical verifier, install/lifecycle/check subprocess и изменение Git/lockfile, но разрешать локальное чтение исходных данных. UI/Electron integration проверяет связь event → persisted result → preview, включая завершение до первого React-render. Одни source.includes/assertIn не являются достаточной проверкой.

**10. Что уже проверено и как сдавать исправление**

Пройдены три Node source-contract проверки: check-human-flow.mjs, check-progressive-contract.mjs, check-baseline-intent.mjs. Они подтверждают нынешний код, в том числе нежелательные продуктовые ограничения, а не исправность пользовательского сценария.

Выбранные Python tests: test_draft_baseline_contract.py, test_block_phi_execution_modes.py, test_block_psi_anytime.py, test_baseline_progress.py, test_block_psi53_search_depth_ux.py. Первый запуск в .venv: 28 passed, 5 failed из-за PermissionError временной папки, 2 subtests passed. Повтор всех шести tests/test_baseline_progress.py с разрешённым доступом к Windows Temp: 6 passed. Итого все 33 выбранных теста прошли; пять первичных отказов не считаются багами продукта. Системный Python не содержит pytest; проектный .venv содержит.

Исправить CI discovery для свободных pytest-функций либо перевести эти тесты в реально исполняемый unittest-контракт. Добавить явную проверку числа собранных Draft-тестов. После реализации выполнить narrow behavioral tests, Electron/React typecheck/build, необходимые существующие regression suites, desktop integration и реальные tiny smoke. Результаты live-прогонов и benchmark не подменять статическими проверками.

Порядок поставки: (1) P0 result/prompt/lifecycle + быстрый Draft; (2) процесс/события/изоляция; (3) режимы и единый deadline; (4) policy от UI до release и миграция legacy; (5) fixtures, интеграционные тесты и документация. Каждый этап должен быть пригоден к проверке. Не увеличивать таймауты и не вводить бесконечные retries как исправление.

В отчёте агента нужны: перечень исправленных причин с файлами; таблица фактического поведения трёх режимов; timings cold/warm/offline на fixtures; пример реально созданного Draft prompt/result manifest; подтверждение сохранности Verified после Draft; единые формулы и принятые пресеты; список оставшихся ограничений. Работа не завершена, пока свежий Draft не выдаёт промпт из Desktop без ручного экспорта и пока выбранная пользователем цель не проходит через весь контракт.
