## H1 — P1. Fast принимает кандидат, который не достиг заданной цели

**Место:** `dependency_live_roadmap_generator.py:5562`, `_candidate_satisfies_fast_policy`; используется реальной веткой `_verified_assignment_satisfies_policy` около 11651 и Fast stop около 11706.

Воспроизведены три независимых случая без обновления установленных версий:

| Вход | Ожидается | Получено |
| --- | --- | --- |
| Два пакета с H:1 каждый, общий maxKnownHigh=1; безопасная версия ещё не выбрана | false | true |
| Green, maxKnownModerate=0, установленный пакет с M:1 | false | true |
| 10 активных пакетов, lag известен и соблюдён только у одного; у девяти lag неизвестен; цель 80% | false: подтверждено 10% scope | true: посчитано 1/1 |

Причины: H сравнивается отдельно для каждой строки с общим лимитом; M/L не проверяются; неизвестные lag-строки исключаются из знаменателя. Исправление прежней ошибки «desired matches вместо цели» не завершило реализацию самой цели.

**Исправить:** оценивать цель на всём активном scope фактического verified candidate; агрегировать security в тех же единицах, что приняты общей acceptance policy; учитывать заданные C/H/M/L; unknown не превращать в подтверждённое соответствие. Версия выше `min_no_*` сама по себе также не доказывает отсутствие уязвимостей в выбранной версии: использовать evidence кандидата, а недостаточные данные оставлять unknown. Физический PASS сборки не заменяет security evidence. Не добавлять физическую проверку в Draft.

**Приёмка:** три сценария таблицы должны стать false; добавить Low и корректные положительные граничные случаи. Проверить настоящую Verified orchestrator-ветку: первый физически прошедший, но не соответствующий policy кандидат не даёт `progressive-fast-policy-satisfied`; следующий соответствующий может остановить Fast; Deep сохраняет incumbent при последующем сбое. Отдельный helper-тест не заменяет этот сценарий.

## H2 — P1. Generate-all всё ещё применяет чужой процент

**Место:** Python `health_yellow_ratio:5111`, `health_planning_ratio:5136`, `compute_project_health:5648–5649,5716`; Desktop `generateAllPolicyEnv:2342` и generate-all env около 2499.

Воспроизведение: общий `EFFECTIVE_MIN_LAG_OK_PCT=80`, для `app-b` в `DEPLOOM_ACCEPTANCE_POLICY_BY_PROJECT` задано 90; 8 из 10 пакетов соблюдают lag. `effective_acceptance_policy('app-b')` правильно возвращает 90, но `compute_project_health` выдаёт `status=yellow`, `lag_needed_for_yellow=0` при фактических 80%. Следовательно, карта доходит до helper, но не до всех вычислений. Задача проекта 90% ошибочно выглядит уже выполненной на уровне health/необходимых обновлений.

**Исправить:** передавать policy конкретного проекта в расчёт health, необходимой доли и planning reserve; устранить использование общего процента в проектных расчётах. Проверить также выбор targetLevel/варианта плана в общем запуске. Не менять policy остальных проектов при выборе текущего проекта в Desktop.

**Приёмка:** один generate-all с A=80%, B=90% и одинаковыми 8/10: у B нужен ещё минимум один compliant пакет, у A порог достигнут; изменение выбранного в UI проекта и порядка проектов не меняет их результаты. Проверять реальные health/plan outputs, а не только возвращаемый объект policy. Для резерва планирования отдельно проверять вычисление от порога соответствующего проекта.

## H3 — P2. Изменение custom groups оставляет Draft «актуальным»

**Место:** `dependency_live_roadmap_generator.py:22330–22331,22593` читает groups; `draft_input_files_for:21384` и вызов около 22647 не включают `groups_config_path`.

Воспроизведена цепочка Python → Node: nested frontend, settings с `groupsConfig: custom-groups.json`. Production `load_group_overrides` сначала возвращает для пакета `lagMonths=12`, после изменения файла — `lagMonths=3`. Input hash остаётся тем же, production `draftResultStaleness` возвращает **`stale=false`**. Сам settings-файл при этом не меняется. Это прежний G3, где custom groups paths прямо входили в приёмку.

**Исправить:** включать реально разрешённый groups-файл в snapshot входов и fingerprint, сохранив Python/Node parity. Учитывать изменение, удаление и появление настроенного входа; не ограничиваться хешированием файла, содержащего ссылку на него.

**Приёмка:** изменение только custom groups даёт stale с причиной; неизменные входы остаются fresh; проверить normal/nested layouts и чтение manifest production Node reader.

## H4 — P2. Closure без доказательств всё ещё возвращает reached=true

**Место:** `desktop/electron/target-closure.ts:127–163`.

Прямой вызов собранного production-модуля:

```js
targetClosureFromRoadmap({
  project_health: { demo: { status: 'green' } },
  projects: { demo: [] }
}, 'demo', 'green')
// reached: true
```

Нет ни lag-доли/знаменателя, ни C/H, ни сведений о security coverage. Отсутствие значений проходит через `undefined || ...`. Это случай старого/неполного roadmap, а не утверждение, что текущий producer всегда создаёт такой документ. Новая проверка явно ненулевого unknown его не закрывает.

**Исправить:** отсутствующие обязательные доказательства означают «недостаточно данных», `reached=false`, с понятной причиной. Legacy-совместимость должна позволять открыть документ, но не превращать цвет в доказательство. Проверять согласованность численных полей; green не должен игнорировать явно ненулевой High из-за старого цвета.

**Приёмка:** приведённый неполный документ не достигает цели; полный корректный документ достигает; пропуски обязательных полей и противоречивые численные данные не дают ложный успех. Это продолжение требования G2 о честном UNKNOWN, не запрет просмотра старых результатов.

## H5 — P2. Заявленные бюджеты режимов не соответствуют обычному Desktop-запуску

**Место:** `desktop/electron/main.ts:2379–2381,2453–2454`; Python `_baseline_max_expensive_attempts`, `_baseline_automatic_budget_seconds`.

Desktop всегда передаёт бюджет и лимит попыток из общего `budgetMinutes`, по умолчанию 30. Поэтому при обычном UI-запуске **и Fast, и Deep получают 1800 s / 3 попытки**. Прямые вызовы Python с этим env подтвердили оба значения. Значения Fast=300s/2 и Deep=3600s/12 из отчёта об исправлении работают только без этих env overrides. Это не означает, что стратегии полностью одинаковы: early-stop Fast подключён отдельно.

**Исправить:** определить и реализовать единый приоритет mode default / явный пользовательский budget / сохранённый legacy budget. Если пользователь осознанно выбрал общий бюджет, одинаковый override допустим; автоматический default не должен незаметно подменять заявленные mode defaults. Показывать реально применяемые пределы и привести документацию в соответствие.

**Приёмка:** проверять command/env, создаваемые настоящим Desktop action для нового intent, сохранённого legacy intent и явного override; затем значения, которые реально использует engine. При переключении mode без пользовательского override поведение соответствует выбранному и отображённому правилу.

## Уже исправленный G4: укрепить тест, не переписывать рабочий код

Новый `test_g4_timed_out_worker_mutations_never_reach_published_rows` задаёт `DeadlineClock(0.2)`. При стандартном finalize reserve=1 s helper выбрасывает timeout **до запуска worker**. Поэтому данный тест не доказывает свой сценарий.

В этой проверке использован deadline=1.3 s и отдельные Events started/proceed/done. Подтверждены запуск worker, timeout, его позднее завершение и неизменность shared `current_version=1.0.0`. Дефект изоляции rows считаю исправленным. В regression-тесте зафиксировать эти события, а не только неизменность rows после паузы; желательно сохранить проверку согласованности публикуемого PARTIAL.
