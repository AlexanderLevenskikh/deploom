## Наблюдаемая проблема и результат для пользователя

После длительного Baseline пользователь дошёл до «Плана обновления», но экспорт завершился ROADMAP_TARGET_DESYNC: строгая lag-policy требовала конкретную версию, а planner явно отложил пакет и оставил target пустым. Позже ТЗ удалось получить, однако кнопка «Скопировать» по сообщению пользователя не работала. Причина clipboard-сбоя пока не воспроизведена. Не объявляй её установленной без проверки.

Пользователь должен пройти основной сценарий целиком в Desktop: увидеть итог/остаток, получить ТЗ, скопировать или сохранить его, отправить выбранному агенту и восстановиться после ошибки. Открытие HTML dashboard не должно быть обязательным. Dashboard оставить подробным отчётом.

Перед реализацией проверь, что исправление вошло в твою ветку, а не предполагай наличие по этому документу.

## Часть 1. Контракт результата и независимый экспорт

1. Подключись к durable state и coordinator накопительной миграции. Не создавай второй управляющий цикл и не определяй завершение по stdout или закрытию процесса.
2. Раздели состояние миграции и состояние подготовки ТЗ. Ошибка подготовки/копирования отчёта не отменяет принятый checkpoint и не запускает поиск или агентскую миграцию повторно.
3. Источник ТЗ — структурированный сохранённый результат: run/project/candidate, base checkpoint, policy/scope hash, точные версии, действия, deferred с причинами, source/dependency identities и реально имеющиеся evidence. HTML и выбранные в нём фильтры не должны определять scope Desktop.
4. Вынеси общий builder/канонический контракт для Desktop и dashboard. Не копируй большую строку промпта в ещё одну реализацию. Возможна поэтапная замена harness, но acceptance требует экспорта без загрузки HTML. Сохрани RU/EN, текущую hash-каноникализацию, validator и правила proof authority.
5. Сохраняй ТЗ и manifest атомарно как связанную версию артефактов с identities и hash. Не заменяй последний валидный комплект неполным. При изменении candidate/policy/source помечай старый комплект stale: его можно открыть как историю, но нельзя незаметно отправить для другого candidate.
6. Старые результаты: при достаточных JSON/evidence перестрой только представление/ТЗ актуальным builder, без полного Baseline и project checks. Если данных недостаточно — конкретная диагностируемая ошибка со списком недостающих полей и действием пользователя. Не придумывай proof и не переписывай исходную evidence.
7. Явно отложенные пакеты сохраняются в остатке и denominator. Строгая policy остаётся невыполненной. Не подставляй lagPolicyTarget в исполняемый target без решения planner; не меняй policy и scopeExcluded для обхода ошибки. Отсутствие обоснованного target, несовпадение identity/hash и недоступный artifact у action-row по-прежнему блокируют небезопасную передачу.
8. Scope текущего candidate и остаток миграции различаются. Deferred-пакет нельзя обновить внутри старого immutable scope; coordinator может включить его в новый candidate с новым manifest после перепланирования.

## Часть 2. Основной сценарий в Desktop

1. В шаге «План обновления» показывай результат без dashboard: принятые обновления, отложенные цели и причины, состояние project checks, актуальность audit, наличие ТЗ/отчётов. Название режима или успешный solver не заменяют project-green.
2. Действия: «Посмотреть ТЗ», «Скопировать», «Сохранить файл», «Отправить агенту», «Повторить подготовку ТЗ». Последнее повторяет только подготовку артефакта для актуального состояния. Согласуй доступность действий с существующим agent authorization; просмотр/копирование не запускает агента.
3. Генерация имеет состояния preparing/ready/failed и видимый timeout. Любой throw/rejection/отмена/закрытие окна гарантированно выводит UI из busy. Пользователь получает понятную причину и точечный retry, а не бесконечный spinner или сырую трассировку вместо основного экрана.
4. После перезапуска приложение восстанавливает принятый checkpoint, состояние шага и последний валидный комплект. Повторный клик/двойной клик/запоздалый ответ не создаёт второй agent run, не перезаписывает артефакт нового candidate и не списывает новую попытку.
5. Различай complete, partial, blocked, cancelled и ошибки инфраструктуры средствами существующего coordinator. Полный прогресс только при реально выполненной policy и независимой проверке. Partial — доступный результат с остатком, а не скрытая ошибка и не COMPLETE.

## Часть 3. Надёжное копирование

1. Воспроизведи отказ в реальном Electron-пути: Desktop preview и встроенный dashboard; отдельно внешний браузер/file URL, где поддерживается. Запиши точную причину отказа, версии и контекст, без приватных данных.
2. Для Desktop реализуй узкий typed preload/IPC метод копирования через Electron clipboard. Проверяй sender, тип и допустимый размер payload; не открывай renderer произвольные Node API, filesystem или IPC и не отключай sandbox/contextIsolation.
3. Показывай «Скопировано» только после успешной записи. При отказе — явная ошибка, выделяемый текст, ручное Ctrl+C и сохранение файла. Сбой clipboard не меняет migration state. Для внешнего dashboard сохрани web Clipboard API и понятный ручной fallback.
4. Убери тихое проглатывание ошибки в затронутом пользовательском пути. Проверяй полный текст, Unicode, переносы, длинное ТЗ и последовательное копирование разных кандидатов. Не логируй содержимое prompt и clipboard.

## Часть 4. Доказательная приёмка

Добавь воспроизводимые synthetic fixtures без приватных имён/registry. Проверяй production boundaries, а не только функцию, возвращающую заранее подготовленный статус.

- Частичный план: одна допустимая action-row + строгая policy с exact planner deferral. ТЗ выгружается, manifest проходит validator, deferred остаётся неизменяемым и в остатке.
- Необъяснённый/stale deferral, несовпадение current/desired, изменённый hash, недоступный target artifact: передача блокируется с причиной; UI выходит из busy; checkpoint сохранён.
- Экспорт при отсутствующем/старом/неоткрываемом HTML из достаточного JSON работает. Недостаточный JSON даёт отдельную ошибку, без запуска Baseline.
- Kill/restart между checkpoint acceptance и записью ТЗ, а также между записью и UI acknowledgement: восстановление без потери checkpoint и дубликата dispatch.
- Ошибка диска, timeout builder, clipboard rejection, отмена и повторный клик: понятный исход, корректный retry, нет вечного busy.
- Candidate сменился во время экспорта/preview: устаревший ответ не становится ТЗ нового candidate; отправка stale scope запрещена.
- Все действия основного сценария доступны в Desktop; ни инструкция, ни recovery не требуют ручного экспорта из dashboard.
- Unit/contract checks дополни проверкой настоящего Electron clipboard (запись/чтение на synthetic тексте в разрешённой тестовой среде) и UI-путём. Mock writeText не доказывает исправление пользовательского сбоя. Не считывай личное содержимое clipboard в логи; пользовательский clipboard не трогай без необходимости.
- Реальный уже завершённый run при доступности используй read-only для проверки экспорта/валидации; не перезапускай многочасовую миграцию ради кнопки. Если реальная проверка недоступна, зафиксируй ограничение, не объявляй её пройденной.

Сохрани требования основного задания к промежуточным метрикам, независимому audit и обоим migration-документам. Экспорт ТЗ не доказывает успешную миграцию, наличие отчётов — полноту policy, успешный clipboard — готовность agent handoff.
