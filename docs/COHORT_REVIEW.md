# Cohort review and audit goals

Desktop asks for cohort approval before materialization, in both manual mode and Autopilot. The per-project **Review dependency cohorts before updating** preference defaults to enabled and survives restart. Disabling it allows the coordinator to continue automatically.

The dialog shows each proposed package and its installed and target versions. Peer-connected atomic groups are selected together. Approving the complete proposal records its candidate, base checkpoint, policy and assignment; changing any of these invalidates approval. Excluding packages or deferring the cohort records a human scheduling deferral, never an incompatibility constraint. The next proposal is re-planned from the last verified checkpoint and requires approval again. Excluded packages remain in the original goal denominator; a deferred required target cannot produce a completed result. Deferred choices apply to this run; changing the run scope is a separate action.

For audit-policy runs, the coordinator audits each accepted checkpoint before selecting another cohort. When the audit passes and all explicitly required versions match, it finishes instead of pursuing every optional proposal. Exact-target runs retain their exact-version goals. Unknown evidence cannot establish completion. An authoritative security audit can establish that a goal fails even when publication metadata is incomplete; a passing result still requires complete evidence.

**Baseline source branch** defaults to `master` and is independent of the update branch. Refresh and verified Baseline use the configured source branch through the existing fetch/clean-checkout/provenance guard; dirty, ahead or divergent work is preserved and blocks switching. Draft remains planning-only. Both branch fields offer searchable local and cached configured-remote refs, deduplicated by logical branch name; listing does not fetch. A branch name can also be entered manually.

**Refresh all** collects a fresh current-state audit for every configured project, including projects that have not been selected or checked. It does not start migrations. Project checking is available while the independent initial audit runs. Current-state audit caches are tied to dependency files, registry configuration, runtime and selected policy; changes invalidate the cache. The UI distinguishes confirmed vulnerability counts from unknown publication dates, explains missing metadata by package, and displays the audited directory and branch. A released branch is not assumed to be the user's currently checked-out directory.

The final delivery agent must create `DEVELOPER_UPGRADE_GUIDE.md` and `MIGRATION_REPORT.md` under `docs/dependency-migration/<run-id>/`, using actual installed upgrades. Widespread Git modifications require inspecting attributes, EOL settings and original/prepared bytes. The agent must not discard changes or normalize entire trees to suppress noise. Delivery continues to require exact verified source bytes, fresh project checks and independent audit evidence.
