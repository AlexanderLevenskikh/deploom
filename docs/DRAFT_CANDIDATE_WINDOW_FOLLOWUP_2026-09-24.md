# Draft: ограничение кандидатов скрывает актуальные версии

## Подтверждённый дефект (P1)

В v0.2.129 Draft обработал 77/77 зависимостей и выпустил DRAFT_READY, но план не позволяет достичь выбранной цели yellow (80% пакетов в lag-policy). В обезличенном реальном запуске активный scope — 76 пакетов, lag OK — 12, lag blockers — 63. В `plan.json` предложено 10 обновлений; 53 из 63 lag blockers имеют статус `no-target`. Один из 10 proposed — peer companion, не закрывающий lag. Проекция после плана — 21/76 (27,6%). Для 80% требуется 61/76, то есть после предложенного плана остаётся разрыв в 40 пакетов; внутренний planning buffer 85% требует 65/76 и оставляет разрыв в 44. Также текущий аудит показывает 1 Critical и 5 High.

Причина конкретна: в `dependency_live_roadmap_generator.py` Draft по умолчанию задаёт `draft-max-candidates=3` (около строки 22861), а `versions_from_current` (около строки 3603) обрезает **первые три версии начиная с установленной**, до вычисления `min_by_lag` и `min_by_vuln`. Для старой зависимости эти версии обычно тоже старые. Поэтому `min_by_lag` ошибочно пишет «не найден installable target в configured registry», хотя в том же запуске `latest` и метаданные новых версий известны. В результате `plan_target_yellow` не получает безопасный lag target, а prompt прячет 53 нарушителя в разделе «Нет проверяемого target», подставляя вместо диагностической причины общую классификацию группы. Это не отказ Nexus и не недостающая security информация. Локальный синтетический вызов существующих функций воспроизводит: список версий 1.0.0–1.0.10, первые три старые — `min_by_lag` сообщает отсутствие target; полный список находит 1.0.4.

Из самого числа 53 **не следует**, что нужно ровно 53 proposed: это текущие нарушители lag-policy без назначенной цели. Допустимый оптимальный yellow-план может обновить меньше пакетов, если достигнет 61/76 и выполнит security-пороги; реальные peer/registry/compatibility блокеры должны остаться явными.

## Что исправить

1. Развязать ограничение количества дорогих OSV/проверочных запросов и поиск по полной **локально доступной registry metadata**. При выборе кандидатов для lag-policy рассматривать версии по всему диапазону от current до latest: минимум первый подходящий по 12/9/6/3 месяцам, подходящие безопасные security-версии и необходимые peer/cohort альтернативы. Проверять, что выбранная версия присутствует в metadata, имеет допустимый tarball URL в настроенном registry и удовлетворяет точной политике. Draft сохраняет PLANNING_ONLY и не выполняет physical install/tarball checks.
2. Если пользователь явно ограничил поиск и из-за этого не исследованы пригодные версии, отражать `candidate-search-truncated` как отдельную причину, а не `no-target`, `registry unavailable` или доказанное отсутствие installable target. Значение по умолчанию не должно скрывать достаточную для достижения цели версию. Не решать проблему только безлимитным OSV-запросом ко всем версиям без оценки времени на 77 пакетах.
3. Разделить в `plan.json` и prompt строки: уже удовлетворяют политике / имеют конкретный target / теоретический target заблокирован конкретным peer или registry условием / поиск ограничен / нет безопасного target по полным данным / неизвестна security. Для `no-target` показывать реальную причину планировщика, а не текст `row.reason` о группе. Раздел «Нет проверяемого target» не должен содержать заведомо актуальные строки. В `result.json` и UI показывать число `no-target` (сейчас 66), чтобы 10 proposed не выглядели полным результатом для 77 строк.
4. В Draft prompt и UI показывать current и projected lag OK по **полному active scope**, требуемое число для yellow/green, остаточный разрыв и известные C/H блокеры. `DRAFT_READY` означает завершённую обработку, но не достижение цели; это должно быть очевидно. Если после поиска план заведомо не закрывает цель, явно назвать его частичным по цели и указать причины/следующие действия. Не выдавать агенту инструкцию «не менять deferred/no-target» так, чтобы она блокировала достижение указанной в том же prompt цели без ясного объяснения.
5. Проверить влияние выбора новых кандидатных версий на точный OSV, peer resolution, registry structural policy, дедлайн и инкрементальную публикацию из R11. Не ослаблять unknown-security и physical verification границы.

## Приёмка

- Failing-first тест: metadata содержит много старых версий и свежую пригодную версию далеко за первой тройкой; Draft на дефолтных настройках находит теоретический target. Отдельно проверить случай с намеренно установленным лимитом и честной меткой `candidate-search-truncated`.
- Сквозной тест: при 80% yellow target опубликованные `proposed` и health projection согласованы, а целевой shortfall либо равен нулю, либо перечислены конкретные blockers с доказательствами. Проверить знаменатель полного scope, security и один peer companion, который сам не улучшает lag.
- Повторить реальный 77-пакетный Draft с теми же входами, сохранить обезличенные `result.json`, `plan.json` и prompt. Сравнить 53 прежде безцелевых lag blockers с новыми статусами, число целей, projected lag OK и время выполнения. Не требовать механически `proposed=53`; требовать план, способный обоснованно приблизиться к 80%, либо честно показать, почему это невозможно.
- Прогнать адресные и полный Python/Desktop регресс, CI. Показать failing-first до исправления. Не публиковать приватные registry URL, пути или имена проекта в публичном отчёте.
